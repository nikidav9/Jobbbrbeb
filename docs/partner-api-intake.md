# Что запросить у первого API-партнёра

Этот файл нужен перед контрактными тестами реальной интеграции. Он **не задаёт
партнёру нашу схему** и не подменяет его документацию: нам нужны фактические
примеры того, что его API действительно принимает и возвращает.

Наш ожидаемый формат фида описан в `docs/feed-format.md`, а уже построенный
embedded-контур JobToo — в `docs/partner-application-api.md`.

## Минимальный пакет, после которого можно писать contract-тесты

### 1. Фид вакансий

Нужен один из двух вариантов:

- тестовый HTTPS URL фида + способ авторизации; или
- сохранённые raw HTTP request/response из sandbox без секретов.

Просим прислать:

- успешный ответ с несколькими реальными по форме вакансиями;
- пример сменной и постоянной вакансии, если API отдаёт оба типа;
- первую и последнюю страницу, если есть пагинация;
- фактическую семантику удаления/закрытия вакансии: флаг, исчезновение из
  полного фида или отдельное событие;
- один реальный ошибочный ответ API, если у партнёра есть стандартный формат
  ошибок.

Для примеров не нужны настоящие контакты людей. Секреты и токены надо заменить
на `***`, но имена заголовков и тип авторизации оставить.

### 2. Создание отклика

Нужны фактические данные партнёра, а не предположение JobToo:

- endpoint, HTTP method и auth;
- пример валидного запроса;
- пример успешного ответа;
- как партнёр возвращает свой ID отклика;
- что происходит при повторе того же логического отклика;
- один пример validation/client error и один transient/server error;
- документированное или наблюдаемое правило idempotency, если оно есть.

Отдельный обязательный ответ: **можно ли вообще создать отклик из внешнего
сервиса**. Если нет, интеграция должна остаться `redirect`, а не имитировать
встроенный отклик.

### 3. Решение по отклику и жизненный цикл смены

Просим полный список **реальных** статусов партнёра и способ их получения:
callback/webhook, polling или оба варианта.

Для каждого фактически поддерживаемого перехода нужны примеры payload/response.
Особенно важно понять:

- каким ID связывается событие с созданным откликом;
- есть ли уникальный ID события;
- есть ли версия/sequence или другой способ определить порядок событий;
- есть ли timestamp события и в каком формате;
- какие статусы терминальные;
- как сообщается факт выхода/завершения/отмены, если такие факты вообще
  доступны через API;
- что партнёр делает при повторной доставке callback.

Если используется webhook, нужны также фактический алгоритм подписи,
заголовки, окно допустимого времени и политика повторов партнёра.

### 4. Чат, если он существует в API

Если партнёр разрешает переписку через API, нужны endpoint'ы и по одному
примеру отправки и получения сообщения, правила идентификаторов и повторов.

Если чата в API нет, достаточно явного ответа **«чат через API не
поддерживается»** — тогда JobToo не будет строить несуществующий контракт.

### 5. Эксплуатационные ограничения

Нужны значения или ссылка на официальную документацию для:

- sandbox/base URL и production base URL;
- способа получения/ротации credentials;
- rate limits и реакции на превышение;
- максимального размера страницы/ответа, если ограничен;
- timeout/retry рекомендаций;
- maintenance/deprecation/versioning политики API, если она есть;
- IP allowlist/mTLS/VPN требований, если используются.

## Как прислать примеры безопасно

Достаточно каталога или архива с текстовыми файлами, например:

```text
feed-page-1.json
feed-page-last.json
application-submit-request.json
application-submit-success.json
application-submit-validation-error.json
application-submit-transient-error.json
status-events.jsonl
headers.txt
notes.md
```

Секреты, реальные телефоны, ФИО и другие персональные данные нужно удалить или
заменить фиктивными значениями. При этом названия полей, заголовков, типы и
структура JSON должны остаться такими, как в настоящем API.

## Что JobToo сделает после получения

Мы фиксируем полученные ответы как обезличенные fixtures и пишем тесты **по
реальному контракту партнёра**:

1. разбор и пагинация фида;
2. нормализация вакансий без потери обязательных данных;
3. создание отклика и фактическая idempotency-семантика;
4. классификация permanent/transient ошибок для retry;
5. сопоставление партнёрских статусов с состояниями JobToo;
6. порядок, повтор и подпись callback-событий;
7. один end-to-end сценарий: вакансия → отклик → решение → доступный партнёру
   итог смены.

Только после прохождения этих тестов источник можно переводить из sandbox в
production/`embedded`. До этого безопасный режим — `redirect`.

## Самые короткие вопросы партнёру

Если документации ещё нет, для старта достаточно ответить и приложить примеры
к пяти вопросам:

1. Где и как забрать тестовый фид вакансий?
2. Можно ли внешнему сервису создать отклик, и каким запросом?
3. Как мы узнаём решение по отклику?
4. Как мы узнаём итог смены и в каком наборе статусов?
5. Есть ли sandbox, rate limit и механизм подписи/авторизации?

Этого пакета достаточно, чтобы следующий шаг был не проектированием наугад, а
воспроизводимыми contract-тестами конкретного партнёра.
